## 2026-02-05 - Substring Check Flaw in Default Secret Validation
**Vulnerability:** The application used `if key in ("super-secret, somethingrandom")` to check for insecure default keys. This logic, intended to check against a tuple of bad keys, was actually checking if the key was a *substring* of the string literal `"super-secret, somethingrandom"`. This allowed weak keys (like "secret") to be flagged as insecure (correctly, but accidentally) but also allowed "super-secret" to be used as a default if the check was intended to block it (it warned but proceeded). The primary issue was the default hardcoded key "super-secret" itself, which allows full account takeover if not changed.
**Learning:** Python tuples with a single element require a trailing comma `("item",)`. Without it, parentheses just group the expression. `("item")` is a string. `in` on a string performs a substring check, whereas `in` on a tuple checks for membership.
**Prevention:** Always verify tuple syntax, especially for single-element tuples. Use `ruff` or linters that catch "tuple with one element missing comma" (though here it was ambiguous). Prefer explicit `["item"]` lists for membership checks to avoid this ambiguity. For security critical defaults, do not allow the application to start with known secrets; generate random ones at runtime if missing.
